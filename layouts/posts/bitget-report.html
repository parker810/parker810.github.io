Bitget热钱包安全事件分析

链上可确认：Bitget 控制地址发出了密码学上有效的多链交易。 Bitget 将事件归因于高权限凭证遭滥用及钱包后端被操控，并称这些划转未经业务审批，且当前调查已排除私钥泄露。

根因与内部响应时间线主要来自 Bitget；Hypernative 独立分析了链上时序、估值和部分交易参数。

结论摘要

链上可确认签名有效；Bitget 称对应资金划转未经业务审批。 Bitget 称攻击者取得高权限内部凭证后，绕过正常订单流程，在钱包后端注入未经授权的提现执行任务， 使钱包系统完成签名和广播；该内部执行路径仍待独立取证报告验证。

证据边界

链上与公开数据可验证
  • 相关地址在 18:31–21:23 UTC 发出了密码学上有效的多链交易。
  • 涉案资产、接收地址、交易金额和链上时序可以独立核验。
  • Hypernative 估算约 $386.5M，并对部分 EVM 交易识别出异常 gasLimit。
  • 链上本身无法判断交易是否经过真实业务审批，也不能证明私钥是否泄露。
Bitget 当前披露
  • 疑似第三方安全产品漏洞导致高权限内部凭证失陷。
  • 攻击者向钱包后端注入未经授权的提现执行任务，并删除关联业务记录。
  • Bitget 称私钥未泄露、冷钱包未受影响，用户余额由保护基金保障。
  • Bitget 公布了对账、应急响应、冷钱包归集和签名服务关闭时间线。
  • Bitget 称已聘请 Mandiant 与慢雾支持独立取证。

  • 被盗凭证的具体权限、来源和有效期。

攻击链

01 Bitget 初步归因，未独立确认 疑似第三方安全产品漏洞

Bitget 直播称其为零日漏洞；厂商、漏洞编号、受影响版本与利用链尚未公开。

02 Bitget 披露 高权限内部凭证

攻击者使用真实有效的账号或凭证进入关键管理系统，活动表现为正常登录和运维。

03 Bitget 披露 注入未经授权的提现执行任务

跳过正常提现记录的生成流程，直接在钱包执行层创建或投递提现执行任务。

04 签名有效可链上验证；内部路径来自 Bitget 披露 交易获得密码学上有效的签名

链上可确认相应钱包密钥生成了有效签名，但无法确认签名发生在哪个内部组件。

05 资金转移可验证；删除记录为 Bitget 披露 多链资金转移与记录清理

多链资金流出可独立核验；删除异常提现执行任务及关联记录属于 Bitget 的调查陈述。

高置信推测

钱包后端存在可创建或投递提现执行任务的业务层；跨链集中转出表明可能存在统一编排 或协调自动化。“关闭签名服务”只说明该功能可被停用，不能证明其部署或权限边界。

仍然未知

提现执行任务的载体究竟是数据库记录还是消息队列事件、签名机数量与部署方式、私钥是否使用 HSM/MPC、 审批凭证格式及第三方产品在网络中的具体位置。

与公开现象相容的一种控制缺口解释 签名前可能未能以攻击者无法篡改的授权记录约束收款地址、资产和金额。 该控制究竟不存在、被绕过，还是其信任根同时受损，目前无法从公开材料确定， 最终仍需等待独立取证报告验证。

基于当前证据的控制缺口假设

01
调用身份本身不足以独立约束资金划转意图

凭证有效只能证明调用身份，不能单独证明目的地址、资产、金额和提现订单经过有效审批。

02
现有风控未约束异常提现执行任务

Bitget 称异常任务绕过了现有风控；公开资料不足以确定风控所在层级，以及其被跳过、禁用还是因记录缺失而未执行。

03
停止用户提现不等于停止签名

时间线显示，03:05 阻断用户提现后链上仍有异常交易，直至 05:44 才关闭签名服务；说明两类控制并非同一开关。

04
检测依赖事后对账

异常在交易广播后才被对账发现，阻断窗口显著缩小。链上交易通常不可撤销，但仍可能通过发行方冻结、执法和追踪追回部分资产。

05
可疑行为信号未形成签名前硬阻断

Bitget 称两笔小额测试低于阈值且未告警；Hypernative 另识别出新地址、异常 gasLimit 和跨链同步转出等信号。

06
业务记录可被攻击路径清除

Bitget 称攻击者删除了异常提现执行任务及关联记录；是否另有独立不可变审计日志尚未公开，不能据此断言其不存在。

07
单点失陷可造成的最大损失范围过大

Hypernative 观察到低频温钱包约 9 秒内在五条网络转出约 $202.8M，说明现有签名前约束未阻止该批交易；具体审批和自动化方式尚未公开。

独立 signer 只隔离密钥使用环境，并不会自动形成业务授权边界。 真正的安全边界来自独立身份、权限、部署、授权账本和签名策略。 Rust 可降低部分内存安全风险，但单独部署、mTLS 与 KMS 均不能替代资金意图校验。

推荐信任架构

本节针对 T1 威胁模型：常规钱包业务服务及其调用凭证完全失陷，而独立授权服务、signer、 密钥存储和策略存储仍可信。其他组件失陷需要分别建模，不能由本方案自动覆盖。
独立授权服务

与常规钱包业务服务分离身份、部署、存储、发布和运维权限；独立读取核心账户/订单事实并执行策略，再对规范化 WithdrawalIntent 调用独立 KMS/HSM 密钥进行数字签名。

→
signer 独立授权账本

验证授权签名、policyVersion、有效期和防重放 nonce，并以只追加方式保存资金意图；队列只是不可信传输层。

↔
常规钱包业务服务（按不可信调用方处理）

只提交 candidateTx。即使完全失陷，也不能创建审批授权或修改资金意图。

授权意图的最小内容

WithdrawalIntent {
  intentId, orderNo, environment, network,
  sourceWalletPolicyId, assetId,
  amountInBaseUnits, destination, memoOrTag,
  allowedAction, feeBounds, policyVersion,
  issuedAt, expiresAt, replayNonce
}

orderNo 只是业务关联标识，不能单独作为授权凭证。 调用方不得提供实际密钥标识；signer 只根据 sourceWalletPolicyId 在内部映射固定账户和密钥策略。

signer 对业务侧暴露的接口

submitWithdrawal(intentId, candidateTransaction) → submissionId

禁止：
decrypt(ciphertext) → privateKey
signHash(keyId, arbitraryBytes) → signature
signBytes(keyId, arbitraryBytes) → signature
selectKeyAndSign(callerSuppliedKeyId, arbitraryTransaction)

signer 使用经审计的链解析库完整解析并规范化 candidateTx；收款方、资产、最小单位整数金额和动作类型 必须与已验签意图一致。nonce、UTXO、recent blockhash 和费用等运行时字段由受控链适配器分配或独立校验； 未知字段、附加输出、附加指令、任意 calldata 和解析歧义一律拒绝。

密钥使用边界

支持相应算法时，优先使用 HSM、MPC 或托管密钥服务的不可导出签名能力，使资金私钥明文不进入 signer 进程。 对托管服务不支持的链或曲线，应单独定义硬件隔离、密钥封装、最短驻留时间和内存清理方案； 禁止把解密后的私钥返回常规钱包业务服务。

幂等状态与广播隔离

AUTHORIZED → CLAIMED → SIGNED → QUEUED
           → BROADCAST → CONFIRMED / EXPIRED

以 (intentId, canonicalTxDigest) 为唯一幂等键。签名结果先持久化到只追加的事务性 outbox，再对外释放； 广播结果不明时不得重新构造或签署不同交易。为缩小最高信任组件的攻击面，signer 不直接访问公网 RPC： 由无密钥的独立广播器通过白名单 RPC 投递，独立观察器负责确认和对账。

逐链交易语义校验（示例；必须覆盖实际启用的每条链）

链类型 signer 必须独立核对
EVM / ETH / BSC 从受控密钥派生发送方；校验 chainId、交易类型、nonce 唯一性、原生 value，或严格解码白名单 token 合约的固定 transfer 调用；限制 gasLimit、maxFeePerGas、maxPriorityFeePerGas、access list 及扩展字段。
BTC / BCH 使用可信 UTXO 数据核对 prevout 金额、脚本和所有权；仅允许批准的 sighash 类型、精确收款输出和受控找零输出；校验绝对手续费、费率、sequence、locktime 及 BCH 重放保护。
Solana 校验 fee payer、program ID、完整 instruction、账户地址及 writable/signer 属性、mint、金额、地址查找表和 durable nonce；recent blockhash 只作运行时新鲜度校验。
TRON 校验网络、ref block、expiration、permission_id、由密钥派生的 owner、合约类型、TRX 金额或严格解析的 TRC20 transfer calldata、合约白名单及 feeLimit。
XRPL 校验由密钥派生的 Account、Destination、DestinationTag、Amount、Sequence、Fee、LastLedgerSequence，以及禁止未批准的 AccountSet、SignerListSet 等操作。
Zcash 核对透明或屏蔽收款方、金额、费用、找零策略、过期高度及所有输出；防止隐藏附加收款方和异常价值差。
Algorand 校验 sender、receiver、asset ID、amount、fee、first/last valid；close remainder、asset close 和 rekey 字段必须符合明确授权。
Cosmos / Celestia 校验 chain ID、account number、sequence、消息类型、denom、最小单位金额、收款地址、fee、gas 与 memo；拒绝附加消息。

针对 T1 威胁模型的优先控制

P0
授权来源独立于常规钱包业务服务

独立授权服务签发 WithdrawalIntent；消息队列只负责传输，signer 必须验签、校验有效期并防重放。

P0
不向业务调用方暴露通用签名原语

signer 内部可调用 HSM/KMS 的 digest 签名能力，但摘要必须由经审计的解析器从已验证交易生成。

P0
幂等签名状态机与 outbox

以 intentId 与规范交易摘要为唯一键；签名结果先持久化，重启或广播不确定时禁止重新构造不同交易。

P0
不可删除的独立证据链

审批、请求、结果和 txid 写入 signer 独立库，并同步至由独立安全账户管理、启用对象锁定/WORM（一次写入、多次读取）保留策略的审计存储。

P0
范围受限的 fail-closed（失败关闭）熔断

仅对已通过授权验证的请求和实际出金计量；新地址、异常参数与跨链速度等组合信号触发按 key/资产/链暂停，避免未认证请求造成全局 DoS；恢复需要独立控制面 M-of-N 批准。

P1
signer 自持密钥与钱包策略映射

WithdrawalIntent 只携带 sourceWalletPolicyId；signer 内部映射固定账户与密钥，拒绝调用方传入 keyId、keyAlias 或 KMS 密文。

P1
限制单点失陷的最大损失范围

设置单笔、钱包、资产、链、钱包层级和全局聚合的滚动窗口硬上限；关联钱包共享预算并检测拆单规避，温钱包大额出金要求独立 M-of-N（多人阈值）批准。

P1
第三方产品零信任隔离

第三方产品不得持有可操作钱包控制面的常驻高权凭证；使用独立管理面、JIT（按需短时）权限、短期凭证和最小网络可达性。

T1 威胁模型验收标准：仅常规钱包业务服务及其调用凭证完全失陷 在独立授权服务、signer、密钥存储和策略存储仍可信的前提下，攻击者最多只能中断服务、 延迟已批准交易，或抢先提交内容完全相同的已批准交易；不能新增提现、改变资金意图、重放授权、 选择任意密钥或绕过额度。授权服务失陷、signer 失陷、队列管理面失陷和 RPC 篡改应作为独立威胁模型另行验收。
